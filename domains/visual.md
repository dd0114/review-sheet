# 영역 노하우 — 화면 · 연출 · 그림 · 소리

> 게임, 프론트엔드, 디자인 시안처럼 **hero 가 눈·귀로 판단하는 결정**에만 적용한다. SKILL.md 공통 규칙 위에 얹는다.
> 백엔드·운영 결정에는 쓰지 않는다(`backend-ops.md`). 프로젝트 고유 주소·도구·화풍 규칙은 그 프로젝트 레포에 둔다.

## 증거 만들기 — hero 가 재현하지 않게
1. **hero 에게 재현 절차를 시키지 않는다.** "이렇게 눌러 보세요" 식 시트는 반려된다. 세션이 그 상태를 headless 로 캡처(또는 상태 딥링크로 열어 찍기)해서 질문마다 `images` 로 붙인다. 이유: 직접 재현하는 데 hero 시간이 가장 많이 든다.
2. **움직임은 정지 화면으로 판단할 수 없다.** 짧은 애니메이션 = GIF(그 동작만 반복되게 잘라서, 처음부터 녹화하지 않는다). 상호작용 = 실제로 돌아가는 HTML 데모를 `links` 로(시트 안 팝업으로 열린다). **webm 은 폰에서 재생되지 않으니 쓰지 않는다.**
3. **실제 표시 크기와 맥락에서 보여 준다.** 그림 단독으로 보여 주면 실제 칸 비율·여백·겹침 문제를 놓친다 → 들어갈 화면에 넣은 캡처를 같이.
4. **소리는 `<audio>` 로 후보 여러 개를 들려준다**(섹션 `html` 또는 링크). 한 개만 들려주고 묻지 않는다.
5. **생성 이미지는 어느 도구·모델로 만들었는지 적는다**(파일별 출처 기록).

## 시안 · 판정
6. **시안은 비교할 수 있게 여러 개**(지정 개수가 있으면 그대로). 이전 확정안과 새 안을 나란히 두고, 이전 안을 고를 수 있는 선택지("이전 것 유지")를 넣는다.
7. **꾸밈만 다른 시안 여러 장은 반려된다** — "무엇을 정해야 하는가"(정보 구조·표시 방식·흐름) 단위로 안을 나누고, 비슷한 다른 제품이 어떻게 하는지 조사해 선택지 근거로 쓴다.
8. **고른 소재는 실제 화면에 입혀서 다시 확인받는다** — 원본 파일 판정 시트를 반복하지 않고, 적용한 화면(테스트 환경)의 캡처·점검 목록으로.
9. **연출(움직임) 변경은 GIF/데모 시트로 합의한 뒤에 머지한다** — 계획·정지 시안 승인만으로는 머지하지 않는다.
10. **그림 일괄 작업은 정지 화면 몇 장 → 확인 → 나머지 → 움직임** 순서. 공통 실수를 앞에서 잡는다(공통 규칙 7).

## 시트 모양
11. 팝업으로 여는 시안·데모가 폰 화면보다 커지지 않게 한다(폭 375px 에서 확인).
12. 질문 수가 많은 판정(예: 그림 수십 장)은 질문마다 그림 1장 + ①통과 ②수정(메모) 두 선택지로 짧게. 답 없는 칸 = 통과.
