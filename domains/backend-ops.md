# 영역 노하우 — 백엔드 · 운영

> PR 승인, 서버·데이터·배포·인프라·성능·정책 결정에 적용한다. SKILL.md 공통 규칙 위에 얹는다.
> 화면·연출 패턴(시안 여러 장, GIF)은 여기서 쓰지 않는다(`visual.md`).
> 실제로 써 본 근거가 있는 것만 담았다. 새 패턴이 굳으면 여기에 추가한다.

## PR 승인 시트
1. **PR 하나 = 섹션 하나.** `now` 에 무엇을 바꿨는지 + 세션이 로컬에서 확인한 결과(테스트 n/n, 충돌 없음). 선택지는 ① 머지 ② 수정 요청(메모) ③ 보류.
2. **증거는 종류에 맞게** — 실행되는 것이 있으면 세션이 직접 돌린 결과(명령과 출력, 관찰한 데이터 변화)를 붙이고, 문서만 바뀐 PR 은 "diff 가 리뷰" 라고 명시한다. GitHub 페이지는 시트 팝업(iframe)에서 안 열리니 핵심 diff·결과를 시트 본문으로 옮긴다.
3. 사람이 직접 확인해 보고 싶을 때를 위해 `table` 2열(직접 해 보기 명령 / 기대 결과)을 덧붙일 수 있다 — 단 주 증거는 세션이 돌린 결과다. hero 에게 명령 실행을 요구하지 않는다.

## 되돌릴 수 없는 작업 (삭제 · 덮어쓰기 · 운영 데이터)
4. **lede 첫 줄에 "되돌릴 수 없음 / 있음"** 을 쓴다.
5. `sit` 에 **백업이 어디에 몇 벌 있는지 + 원본과 같은지 대조한 결과**, `effect` 에 **복구 방법과 걸리는 시간**.
6. **빠뜨리면 반드시 되묻는 정보**: 경로(어디서 어디로), 용량과 남은 여유 공간, 영향받는 사용자 수·범위. 처음부터 넣는다.

## 위험 수준 맞추기
7. **지금 단계를 먼저 밝힌다** — 출시 전 / 사용자 0명 / 테스트 서버 / 운영 중. hero 는 단계에 따라 감수할 위험을 바꾼다. 출시 전에 과하게 신중한 질문(막을 필요 없는 제한, 미리 할 필요 없는 자동화)은 반려된다.
8. **위험이 낮고 되돌릴 수 있는 운영 작업은 묻지 않고 하고 나서 보고한다**(공통 규칙 4). 시트로 묻는 것은 운영 데이터 삭제·구조 변경처럼 비싼 것으로 한정한다.
9. **시점을 고르는 선택지**(배포·재시작·이전)에는 서비스 중단 시간, 문제 시 되돌리는 시간, 사람이 깨어 있는 시간대인지를 같이 적는다.

## 판단 근거 붙이기
10. **성능·비용 판단에는 실측 표** — 단계별 시간과 비율, 병목 한 줄. 실측이 이미 결론을 주면 그 결론(예: "지금은 안 해도 됨")을 추천으로 단다.
11. **숫자(설정값·한도·곡선) 결정에는 표만 말고 전체 그래프** 이미지를 붙인다.
12. **로그 보관·수집 범위 같은 정책**은 개인정보 포함 여부와 용량 추정을 `sit` 에 넣는다.
13. **조사 보고형 시트**("업계에서는 어떻게 하나"): lede 에 결론과 원인 한 줄, 질문은 정책 / 시점 / 범위 3개 정도로 마무리.
